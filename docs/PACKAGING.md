# PACKAGING

How paint.c is packaged for Linux, Windows and macOS, what each package
contains, and how CI builds and releases them (lane I). The files live in
packaging/ (overview: packaging/README.md).

## Common contents

Every package carries:

* the `paintc` executable (`paintc.exe` on Windows, `paint.c.app` on macOS),
  statically linked with SDL3 3.4.18 and the codec libraries when built with
  `-DPC_VENDOR_SDL=ON` (CI does); with a system SDL3 the AppImage bundles
  `libSDL3.so` through linuxdeploy;
* a `licenses` folder: paint.c's MIT `LICENSE.txt`, `NOTICE.txt` (the
  Paint.NET 3.36 attribution) and the texts of every third-party component
  (packaging/licenses, indexed by its README.txt): SDL3, zlib, libspng (with
  the libpng 2.0 license of the code it took from libpng), libjpeg-turbo
  (with the IJG README), libwebp (with PATENTS), Little-CMS, bcdec, bc7enc,
  stb (stb_truetype and stb_dxt) and the Inter font (SIL OFL 1.1);
  tests/app/test_i_packaging.c fails when the folder and its index differ;
* the application icon: an original design (a white pixel dot and a
  color-wheel letter c on a dark blue tile, so ".c"), generated by
  `python3 packaging/icons/make_icons.py` into assets/icons (scalable SVG, a
  heavier small variant for 16 to 32 px, PNGs 16 to 1024, `paintc.ico` with
  PNG entries, `paintc.icns` written by our own encoder) and
  src/app/io/icon_data.c (the 32, 64 and 256 px PNGs for the window icon,
  set with `SDL_SetWindowIcon` at startup). The generated files are
  committed; builds never run the script.

File types: every format the codec registry opens is registered by each
package (PDN, PNG, JPEG, BMP, GIF, TIFF, WebP, TGA, DDS, OpenRaster).
tests/app/test_i_packaging.c compares the installer, the desktop entry, the
AppStream metadata and Info.plist with `pc_codec_list`, so a new codec fails
the test until the packaging knows it.

## Linux

`cmake --install build --prefix <prefix>` installs (packaging/PcPackaging.cmake):

| Path | File |
|---|---|
| bin/paintc | the executable |
| share/applications/io.github.vancevoj.paintc.desktop | desktop entry (`Exec=paintc %F`, MIME types, `StartupWMClass=io.github.vancevoj.paintc`, the SDL app id) |
| share/mime/packages/io.github.vancevoj.paintc.xml | `image/x-paintnet` for `*.pdn` (magic `PDN3`); the other types are in freedesktop.org.xml |
| share/metainfo/io.github.vancevoj.paintc.metainfo.xml | AppStream metadata |
| share/icons/hicolor/{16..512}/apps/io.github.vancevoj.paintc.png, scalable/apps/io.github.vancevoj.paintc.svg | icons |
| share/doc/paintc/licenses/ | licenses |

Distribution packages run `update-desktop-database`, `update-mime-database`
and `gtk-update-icon-cache` as usual.

* **tar.gz**: `cd build && cpack` (CPack TGZ of the install tree).
* **AppImage**: `packaging/linux/build-appimage.sh build dist` installs into
  an AppDir and runs linuxdeploy 1-alpha-20251107-1 (downloaded once,
  SHA-256 checked, cached in `PC_DOWNLOAD_CACHE`), which writes AppRun,
  bundles the shared libraries the binary needs and packs
  `dist/paintc-<version>-linux-x86_64.AppImage`. It works without FUSE
  (`APPIMAGE_EXTRACT_AND_RUN=1`). Verified locally and in CI with
  `--self-test --headless` inside the AppImage.
* **Release AppImage (glibc 2.31 floor, OD-4)**:
  `packaging/linux/build-appimage-docker.sh <work dir> [<output dir>]`
  builds in an Ubuntu 20.04 container (image pinned by digest, GCC 13 from
  the ubuntu-toolchain-r PPA, CMake 3.31 from pip, SDL3's X11 and Wayland
  build dependencies, libdecor 0.2.2 from its release archive), with the
  source mounted read-only, vendored SDL3 and AVIF/JPEG XL `BUNDLED`.
  libstdc++ and libgcc are linked statically (a folder holding only
  `libstdc++.a` is searched first, because the codec link names
  `-lstdc++`), so `paintc` needs only glibc. The script then runs
  build-appimage.sh in the container and fails unless no symbol needs a
  glibc newer than 2.31, DT_NEEDED lists only glibc libraries, no `.so` is
  bundled, and the AppImage passes `--self-test --headless` on Ubuntu
  20.04. `PC_RUN_TESTS=1` also runs every test in the container;
  `PC_DOCKER_CPUS`, `PC_DOCKER_CPUSET`, `PC_DOCKER_MEMORY`, `PC_JOBS` and
  `PC_NICE` limit its load. The AppImage uses the static type 2 runtime
  (needs `fusermount` or `--appimage-extract-and-run`, no libfuse2).
* **Flatpak** (io.github.vancevoj.paintc): `flatpak run
  org.flatpak.Builder --user --install --force-clean build-flatpak
  packaging/flatpak/io.github.vancevoj.paintc.yml` builds this checkout.
  `packaging/flatpak/build-bundle.sh <work dir> <output dir>` builds the
  release bundle `paintc-<version>-linux-x86_64.flatpak`, which GNOME
  Software and KDE Discover install by opening the file (the runtime comes
  from Flathub through `--runtime-repo`). The signed Flatpak repository
  is github.com/vancevoj/paintc-flatpak, served at
  https://vancevoj.github.io/paintc-flatpak/ (install link:
  `io.github.vancevoj.paintc.flatpakref` there); a release goes in with
  `packaging/flatpak/publish-repo.sh <build dir> <checkout of paintc-flatpak>`,
  then a commit and push of that checkout. Its signing key is kept outside
  every repository (`~/.local/share/paintc-flatpak/gnupg` on the owner's
  machine); a new key would make every installed copy reject updates. paint.c
  is not on Flathub (owner's decision). Runtime org.freedesktop.Platform 26.08, whose SDL3 (3.4),
  libavif and libjxl are used (`PC_VENDOR_SDL=OFF`, ADR-022 accepts SDL
  3.4); `PC_WERROR=OFF` so a compiler update in the runtime cannot fail the
  build. Permissions: Wayland with X11 fallback, DRI, the Pictures folder,
  and org.freedesktop.FileManager1 for Open Containing Folder. Other files
  go through the file chooser portal: its documents are persistent, so
  recent files stay readable after a restart, and saving over them works
  through the document portal. The build is offline: the manifest lists
  the five codec dependency archives of cmake/PcDeps.cmake and
  cmake/PcCodecDeps.cmake with the same URLs and SHA-256 and passes them to
  CMake through `PC_DOWNLOAD_CACHE` (keep both lists in sync). The optional
  plugins are not part of the Flatpak: their folder is
  `~/.var/app/io.github.vancevoj.paintc/data/paintc/plugins`. Inside
  Flatpak the single instance socket lives in
  `$XDG_RUNTIME_DIR/app/io.github.vancevoj.paintc` and the Text tool also
  scans the host fonts under `/run/host` (ADR-025). AppStream screenshots
  are packaging/screenshots/*.png, made by
  packaging/screenshots/make-screenshots.sh; the metainfo links them through
  the release tag, so regenerate them before tagging when the UI changes.

## Windows

`cmake --install build --prefix stage` gives `paintc.exe`, `README.txt`
(packaging/windows/README-portable.txt) and `licenses\`. paintc.exe embeds
the manifest (long paths, UTF-8, per-monitor DPI), the icon (all sizes of
paintc.ico) and version information (src/app/platform/paintc_version.rc.in;
numeric constants, so windres, rc.exe and llvm-rc all build it).

* **Portable zip**: the install tree zipped as
  `paintc-<version>-windows-x64-portable.zip`. Settings live in
  `%APPDATA%\paintc`, autosave copies in `%LOCALAPPDATA%\paintc\State`;
  `--config-dir DIR` keeps settings and autosaves under DIR instead.
* **Cross-built release packages**:
  `packaging/windows/build-mingw-release.sh <work dir> [<output dir>]`
  builds with the mingw-w64 toolchain file (Release, vendored SDL3,
  AVIF/JPEG XL `BUNDLED`), installs the stripped tree into
  `<work dir>/stage/paintc-<version>-windows-x64` and writes the portable
  zip (that folder at its top) and the installer (makensis on Linux takes
  `-D` options). `PC_RUN_TESTS=1` runs every test under Wine in
  `<work dir>/wineprefix`.
* **Installer**: `makensis /DVERSION=<v> /DSTAGE=<abs stage>
  /DOUTFILE=<abs exe> packaging\windows\paintc.nsi` (NSIS 3, Unicode,
  per-machine, 64-bit registry view). It installs to Program Files, adds a
  Start menu shortcut for all users and an uninstaller (Apps & features entry), registers
  the program ids `paintc.Image` and `paintc.pdn`, an "Open with" entry for
  every extension, the RegisteredApplications capabilities (Settings >
  Default apps), `Applications\paintc.exe\SupportedTypes`, and makes .pdn
  open with paint.c when no other program claims it (only that default is
  removed again on uninstall). Other types keep their defaults: Windows asks
  the user. Verified: built with makensis 3.11 from the MinGW build,
  installed and uninstalled silently (`/S`) under Wine 10 with the registry
  checked.

## macOS

The build produces `build/paint.c.app` (ADR-001; src/app/CMakeLists.txt
copies `paintc.app`), with `Contents/Resources/paintc.icns` and the
licenses in `Contents/Resources/licenses`. Info.plist
(src/app/platform/Info.plist.in) declares every document type (system UTIs,
imported UTIs for .pdn and .ora), `LSMultipleInstancesProhibited` (one
instance per user: pal's single instance is not implemented on macOS, and
LaunchServices forwards opened documents as drop events without a window,
which paint.c opens directly) and `NSHighResolutionCapable`.

* **dmg**: `packaging/macos/make-dmg.sh build dist` installs the bundle,
  signs it ad hoc (`codesign --force --deep --sign -`), verifies the
  signature and packs it with an /Applications link into
  `dist/paintc-<version>-macos-<arch>.dmg`. Without a Developer ID the
  first start needs right click > Open (Gatekeeper). Notarization needs a
  Developer ID certificate, the hardened runtime and, for plugins from the
  per-user folder (ADR-008), the `com.apple.security.cs.disable-library-validation`
  entitlement; that is OWNER work.

## CI and releases

`.github/workflows/ci.yml` (existing jobs unchanged, packaging steps added):

| Job | Packages (artifact name) |
|---|---|
| linux-gcc | validates the desktop entry (desktop-file-validate) and the AppStream file, builds the tar.gz and the AppImage, runs the AppImage's self test (`pkg-linux-x86_64`) |
| windows-cl | portable zip and installer (`pkg-windows-x64`); NSIS comes from the runner image or Chocolatey |
| macos-14, macos-15-intel | dmg per architecture (`pkg-macos-14`, `pkg-macos-15-intel`); these jobs still run only on dispatch, tags or `[mac]` commits |

`.github/workflows/release.yml` runs on tags `v*`: it checks that the tag is
`v` plus the project version in CMakeLists.txt, calls ci.yml (so every test
runs, macOS included because the ref is a tag), downloads the `pkg-*`
artifacts, writes SHA256SUMS.txt and creates the GitHub release with all of
them (`gh release create --generate-notes`).

### Local releases (no GitHub Actions)

When Actions cannot run (0.1.0: billing, ADR-021) a release is built on a
Linux machine with Docker, mingw-w64, NSIS and Wine: the AppImage with
build-appimage-docker.sh, the Windows zip and installer with
build-mingw-release.sh, from 0.1.2 the Flatpak bundle with
`PC_COMMIT=<commit> packaging/flatpak/build-bundle.sh <work> <dist>`, then
`packaging/release-dist.sh <dist> <commit>`
adds `git archive --prefix=paintc-<v>/` of the release commit as
`paintc-<v>-source.tar.gz` (macOS builds from it, docs/BUILDING.md),
`SHA256SUMS.txt` over all packages and `release-notes.md`
(packaging/RELEASE_NOTES_<v>.md with its `@CHECKSUMS@` line replaced by
the sums; the committed notes keep the placeholder because the source
archive contains them). Then
`gh release create v<v> <packages> SHA256SUMS.txt --target <commit> --notes-file <dist>/release-notes.md`.
The notes say how each platform was verified. Creating the release creates
the tag, which triggers release.yml; while Actions cannot start jobs that
run fails at once, and if it does run, its publish step stops because the
release already exists.

## Optional plugins (separate downloads)

The plugins of plugins/ are not part of any paintc package. They are
released on their own as `plugins-v<version>` (the tag does not match
release.yml's `v*`, so the app release workflow does not run for it), built
and zipped by packaging/plugins/build-plugins.sh: Linux in the same Ubuntu
20.04 container as the AppImage (glibc 2.31 floor checked on every
library), Windows with the mingw-w64 toolchain (UCRT, no MinGW runtime
DLLs). One zip per plugin and platform
(`paintc-plugin-<name>-<version>-<platform>.zip`, a top folder `<name>/`
with the library, README.md, screenshot.png and LICENSE-original.txt when
present), an all-plugins zip per platform and `SHA256SUMS`. The plugin set
version and the repository of the download links are in
packaging/plugins/release.conf; plugin_meta.py turns the README cards of
the plugins into the tables of README.md and docs/PLUGINS.md. Details,
including the release command: docs/PLUGINS.md, Packaging and releasing.

## Out of scope (documented gaps)

* File > Print (Paint.NET: the Windows photo printing wizard) and File >
  Acquire (scanners): not implemented; Print shows disabled, Acquire is
  hidden.
* The AppStream file has no homepage URL until the project has a site
  (`appstreamcli validate` reports `url-homepage-missing`, the only finding).
* No code signing: Windows binaries are unsigned (SmartScreen warns), macOS
  builds are signed ad hoc only.
